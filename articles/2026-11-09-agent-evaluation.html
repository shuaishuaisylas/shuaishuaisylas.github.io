Agent 评测：如何判断你的 Agent 真的变好了？

2026-11-03sylas全文 2971 字

很多 Agent 项目会卡在三个地方：停在上线演示，扩量后问题频发，或者始终说不清业务价值。这些问题背后，往往缺少同一种能力：可靠地判断当前版本行不行、问题出在哪一层、改完到底有没有变好。

评测就是补上这个判断机制。但它远比“给个分数”复杂。

评测的对象变了，这是所有认知的起点

传统机器学习评测更多看“算得准不准”，大模型评测更多看“能力强不强”，Agent 评测要回答的是：当模型和 Prompt、Skill、工具链、记忆、流程放在一起，它能不能稳定交付结果。

评测对象从“一个模型”，变成了“模型与整个执行系统”。

拿一个虚构的账户业绩分析场景来说。投资经理问：“同样执行一个策略，为什么账户 A 这个月跑输账户 B？”

Agent 需要查询资产、持仓、交易和资金流水，统一收益计算口径，再根据证据解释差异。评测既要看报告结论，也要看数据是否完整、计算是否正确、解释是否有依据。

两个 Agent 可能最终都说对了，但一个证据完整、调用稳定，另一个遗漏关键数据、靠猜测碰巧命中。只看最终答案，它们可能被判成同一水平，工程价值却差得很远。

所以评测至少要覆盖四层：结果是否正确，过程是否可靠，效率是否合理，风险是否可控。

这次迁移，可以概括为：从“答案评测”走向“行为与状态评测”。不要求所有任务走同一条路径，但要检查必要约束有没有遵守、最终状态有没有达成。

先降低评测波动，再讨论版本提升

“好不好”经常是主观问题。真正难的不是没人会评，而是不同人评得不一样，人和机器评得也不一样。

例如，同一份账户分析报告，有人觉得结构完整，可以打高分；有人认为缺少归因依据，只能打低分。如果判断标准不稳定，分数涨了，你也不知道是 Agent 变好了，还是这次评得更宽松。

解法是把模糊判断拆成可以核验的问题：

  • 比较口径是否一致：期间、币种、收益率算法、费前或费后口径有没有对齐？

  • 资金流水是否正确处理：有没有把入金当成投资收益？

  • 关键结论是否有证据：数据是否真的支持结论，而不只是附了一个引用？

  • 信息不足时是否正确处理：有没有说明限制，而不是补写原因？

设一个简化样本：A、B 月初都是 100 万元，忽略费用。A 月末资产为 112 万元，其中 10 万元在月末交易结束后转入；B 月末资产为 103 万元，没有资金流动，两个账户期间也没有其他现金流。

这个设定下，A 的收益率为 2%，B 为 3%，A 落后 1 个百分点。若 Agent 直接比较期初、期末资产，就会把 A 算成 12%，甚至围绕错误数字写出一篇“配置有效”的分析。外部现金流及其发生时间，正是收益计算必须处理的因素。GIPS 收益计算说明

这种问题，用“专业程度打几分”很难稳定抓住，用“是否正确处理入金”就容易得多。

不过，稳定不等于正确。降低方差是为了看清变化，校准标准是为了确保变化朝着正确方向。

评测体系是两条环，不是一个看板

一套能运转的体系，可以拆成四个模块：离线评测守住已知，在线评测和监控发现未知，Case 挖掘与归因负责定位问题，观测基建提供证据。

它们组成两条相互连接的闭环：

  • 评测体系迭代环：线上信号 → Case 挖掘 → 归因 → 补评测集、修评分标准 → 回测。

  • Agent 迭代环：同批样本 → 定位数据、工具、Prompt 或模型问题 → 修复 → 回测 → 小流量验证。

还是刚才的账户案例。通过 Trace 发现，查询工具已经返回了 10 万元入金，但后续计算工具的参数里没有这条现金流。

Agent 这一侧，要修复字段传递。评测这一侧，要把这个案例沉淀下来，再补充月中入金、多次出金、流水缺失等变体。

前者解决这一次错误，后者让以后每次改动都能检查同类问题。

两条环的连接点，就是不断积累的评测资产。

一个隐蔽陷阱：Agent 会学会迎合评测

归因之后有两条路径：可能是 Agent 做错了，也可能是评测判错了。

很多团队只走第一条，默认“评测说不行，就是 Agent 不行”。这会让 Agent 逐渐迎合评分规则，而不是解决用户问题。

比如，账户分析的评分标准规定：“优秀报告必须包含行业配置、个股选择和交易时点三个方面的解释。”

听起来很全面，但如果当前只有资产和资金流水，没有必要的历史持仓与交易数据，这个要求就可能逼着 Agent 编原因。

此时，更好的回答应该是：“已确认 A 落后 B 1 个百分点，但现有数据不足以解释差异来源。”

知道差了多少，不等于知道为什么差。评测必须允许有依据地缩小结论，也必须识别没有依据的完整答案。

所以，定期检查“是不是标准在奖励错误行为”，是体系自我校准的必要动作。

离线守住已知，在线发现未知

离线评测的核心是控制变量：固定样本、固定标准、固定执行环境，再比较不同版本的表现。

金融场景里，最容易破坏可比性的是数据口径和时间。昨天的行情、今天的持仓、后来修订的净值，如果被混在同一个样本里，分数变化就未必来自 Agent。

因此，一个账户分析样本不能只有用户问题和参考答案，还要保存必要的数据快照、计算口径和预期结果。

但离线有硬边界：评测集没覆盖的场景，回测很难发现。

如果样本都是人民币账户、单月比较、没有资金流动，上线后用户开始查询跨币种账户、跨季度收益和频繁申赎，原来的高分就不足以说明系统仍然可靠。

在线部分可以分两类：固定样本巡检检查旧能力有没有退化，真实任务抽样发现新问题。两者不能相互替代。

监控时，也要把业务结果和过程信号合起来看。完成率下降，如果同时出现数据接口失败增加，应先排查工程链路；如果接口正常，但跨币种和复杂现金流任务明显增多，就要检查场景覆盖和任务结构变化。

同样是完成率下降，背后的问题可能完全不同。

别一上手就设计完美体系

Agent 评测是实践工作。起步阶段，让“发现问题—修复—验证”的循环转起来，通常比设计一套复杂指标更有价值。

账户分析场景可以先从少量核心样本开始：正常账户比较、含入出金的比较、数据缺失、口径冲突、无权访问。

先收 Bad Case，再沉淀 Good Case，明确什么叫“好”；把它们转成标准样本，反哺 Prompt、Skill 和工具流程，再进入下一轮。

这里的 Good Case 也不全是漂亮的完整报告。正确识别口径冲突、发现数据缺失后停止归因、拒绝读取无权访问的账户，都可以是好结果。

指标应该随着真实问题增长，而不是为了显得完整，提前列出几百项。

落到实际工作里的三条判断

如果正在做或准备做 Agent 评测，我觉得最值得带走的是这三条：

  1. 先问有没有 Trace。 冷启动至少要做到“最小可归因”：能看到关键模型输入输出、工具参数和返回结果，结合当时的数据还原一个 Bad Case。否则，最终报告错了，你很难知道该改哪里。

  2. 警惕“两头都有，中间断了”。 既有评测集，也有监控看板，但线上错误回不到评测集，修复后也没有回测。这种形态看起来完备，实际上很难持续积累质量。

  3. 先补最影响判断的短板。 没有可信的收益计算结果，就先补计算依据；看不到调用过程，就先补观测；已经能定位问题却总是复发，就补回测门禁。投入应该服务于当前最关键的缺口。

评测体系的本质，是把团队对业务质量的隐性认知，转化为可核验、可复用、可传递、可执行的资产。

在账户分析里，这些认知可能只是几条朴素的规则：比较要统一口径，入金不能直接当收益，归因必须有证据，数据不足就明确说明。

当这些规则能够被反复执行，并帮助团队发现问题、定位问题、验证改进时，评测才真正开始发挥作用。

它的价值不只在上线那天，也在半年后，你仍然能说清：“为什么这个版本比上个版本好。”
